# Multiplayer Mode UI and Admission Inventory

Static source inventory for placing a pre-session Native/Experimental selector and rejecting unsupported or mismatched sessions before world load. This is a hook-point map, not an implemented mode selector. `runtime/ExperimentalMode.cs` is not currently referenced by the game bridge; the only callers found are tests.

## Existing options UI install path

- Main settings are `settingsscript`; `settingsscript.FStart()` assigns the singleton, initializes defaults, loads saved settings, then refreshes the menu. `settingsscript.Start()` initially closes tabs. `settingsscript.tabMisc` contains `obj`, `toggles`, `dropdrops`, and `sliders`; `PressedTab(int)` opens it for tab index 3. `RefreshMenu()`/`RefreshInMain()` read current UI arrays and game settings.
- Existing Roadworthy UI is a precedent: `StableGameBridge.Bootstrap()` adds a persistent `PatchOptionsMenu` component. `PatchOptionsMenu.Update()` waits until `settingsscript.s` is active, then 10 active frames and calls `Install(settings)`. `InstallMisc(settings)` clones the first native `togglesetting` row under `settings.tabMisc`, labels/configures it, appends to `tab.toggles` and `tab.obj`, and stores changes in `PatchOptions`' external options file. Existing rows include car smoothing, rabbits, sandstorms and high update rate. This preserves native settings serialization and index-based rows, but installing only at multiplayer Bootstrap may make the selector unavailable before the network UI initializes; confirm startup order or attach the installer earlier.
- A mode selector belongs before multiplayer join/create, so the **main Settings Misc** tab is a viable pre-session location. The `SteamP2PMenuHandlerScript` also has its own settings screen (`PressedSettings`) for notification/voice/chat preferences; that UI is not the main Settings Misc tab and is not wired to mode selection.
- No Experimental mode toggle, persistence key, or `ModeLatch` instance is currently wired. `ModeLatch.Select(mode)` rejects selection while in session; `Begin(experimentalBackendReady)` refuses Experimental if backend is not ready and locks `Active`; `End()` clears session and sets `Active=Native`, while leaving `Selected` as the user's next-session choice. These are pure model methods, not actual lobby hooks today.

## Admission and pre-mutation points

| Point | Existing native method / action | Opportunity and ordering constraint |
|---|---|---|
| Host presses Create | `SteamP2PMenuHandlerScript.APressedCreate()` calls `PressedAnything()` then `SteamMatchmaking.CreateLobby(...)`. | Check selected mode/backend support before the Steam call. This is the earliest host guard; deny Experimental before a lobby is created if backend is absent. |
| Guest chooses lobby | `APressedLobby(CSteamID)` changes `hood.SelectedLobbyID`; a double-click calls `APressedConnect(false)`. | Selection alone does not join. Lobby metadata may be inspected here for immediate UI feedback, but connect must revalidate because the selected lobby can change. |
| Guest presses Connect | `APressedConnect(bool)` first handles password prompt; after password acceptance it may disconnect the current lobby, calls `PressedHide()`, then `SteamMatchmaking.JoinLobby(SelectedLobbyID)`. | Compare selected mode with target lobby's advertised mode/protocol **before** disconnecting the current session and before `JoinLobby`. If a password prompt intervenes, repeat the same check in the password-confirm path (`APressedPasswordOk()`→`APressedConnect(true)`). |
| Steam creates host lobby | `SteamP2PNetworkingUnderTheHoodScript.OnCreatedLobby(LobbyCreated_t)` on success sets `isHost=true`, `ConnectedLobbyID`, lobby `name`, `map`, `version`, spawn type, physics lock and password. | Defensive failure cleanup belongs at callback if pre-create state is stale; the lobby already exists at this stage, so this is later than `APressedCreate`. Mode metadata must be published here after creation if lobby data is used for discovery. |
| Steam enters guest lobby | `OnLobbyEnter(LobbyEnter_t)` success sets `isConnected=true`, `ConnectedLobbyID`, password state and log. | Final compatibility fallback can immediately leave/clear a mismatched lobby before allowing host protocol or world traffic. Lobby membership has already changed, so this is a safety net, not the desired first rejection point. |
| Client world bootstrap | `SteamP2PNetworkingUnderTheHoodScript.ClientSendOnJoin()` sends password if needed; authenticated host path `networkingScript.HostSendOnJoin(client)` calls `syncScript.SendMapStuff(client)` (plus time). | Do not send/apply the native bootstrap when Experimental mode is active, unless the two modes are deliberately interoperable. Gate sender and receiver consistently. |
| Guest world mutation | `networkingScript.ProcessMessage` routes native `msgType.mapStuff` to `syncScript.RecMapStuff`. `RecMapStuff` calls `DataFromMenuScript.ResetStuff()`, `SetMulti(true)`, populates map/seed/host position and calls `menuhandler.LoadScene()`. | Last native-mode veto must run before this receiver or at `AllowIncoming` for `mapStuff`. Once dispatched, map/menu scene transition has started. |
| World scene creation | `menuhandler.LoadScene()` starts `DoLoadScene()`, which displays loading text and calls `SceneManager.LoadScene(sceneName)`. New single-player start is `menuhandler.PressedStart()`→`ResetStuff()`→`newgame=true`→`LoadScene()`. | Mode lock and world-session policy must distinguish a multiplayer bootstrap from a local new game/load. Don't globally gate `LoadScene()` on a selected mode. |
| Leaving / switching worlds | `menuhandler.PressedMainMenu()` calls `syncScript.Disconnect()` when connected, then `LoadMainMenu(true)`; hood `Disconnect(string)` leaves the Steam lobby and clears native connection/host/password flags. `StableGameBridge.Reset()` is invoked by bridge `Ensure()` after native disconnection. | End `ModeLatch` only after transport/node teardown is complete; preserve `Selected` for the next session. On failed join/host creation, unwind a pending begin so UI can select again. |

## Lobby metadata currently available

- Native host `OnCreatedLobby` writes lobby keys `name`, `map`, `version`, plus spawn type/physics lock/password metadata. Guest browsing in `SteamP2PMenuHandlerScript.UpdLobbies(LobbyMatchList_t)` reads lobby data; `PatchStability` replaces the native version-key write in `OnCreatedLobby` through `StableGameBridge.SetLobbyVersion` and version read in `UpdLobbies` through `GetLobbyVersion`.
- `SetLobbyVersion(lobby,key,version)` writes the requested native value and `roadworthy_version=PatchInfo.Display`; `GetLobbyVersion` returns Roadworthy version if present, else native app version. This is a version compatibility label, not a mode field. A separate mode/protocol metadata key and policy are not present.
- `APressedConnect` has a `SelectedLobbyID` before disconnect/join and can read lobby data then. `APressedLobby` only selects the target and a double click delegates to Connect. For discoverability, `UpdLobbies` is the place where a lobby row can be labelled/disabled, but a click/connect guard remains necessary.

## Session lock and mode lifetime

- Intended model: persistent next-session preference `Selected`; call `ModeLatch.Begin(backendReady)` only after preflight passes and immediately before the irreversible lobby attempt; lock choice while `InSession`; if async create/join fails, abort/End; on successful disconnect/world teardown, `End()` releases lock while preserving selection.
- Host create preflight can begin before `CreateLobby`; if `OnCreatedLobby` reports failure, release the pending latch. For clients, do not begin/lock on row selection or while a password prompt is pending; validate chosen lobby, then begin immediately before `JoinLobby` after password entry.
- `OnLobbyEnter` / `OnCreatedLobby` are asynchronous callbacks and can report errors after preflight. They must reconcile mode state and transport initialization on every success/failure branch. Existing `ModeLatch` has only `Begin`/`End`; no explicit abort reason or async attempt token exists.
- Switching to another lobby from `APressedConnect` first disconnects the current one; a blocked target should be rejected before that disconnect to avoid destroying the valid current session.
- Main menu return explicitly disconnects via `PressedMainMenu`; disconnect may also happen through `APressedDisconnect`, kick/password failure (`KickHandle`), Steam leave callbacks and transport loss. All routes need converge on one teardown/end path; source review has not exhaustively traced every failure/callback ordering.

## Exact settings install considerations

- `settingsscript.tabMisc.toggles` is index-read for native game fields inside `RefreshMenu()`; append a new row without inserting/reordering native entries. The current `PatchOptionsMenu.InstallMisc` already appends custom rows, and cloned rows clear `settings`, `childToggles`, `dropdown`, `button`, and event state before wiring their own callback.
- The `PatchOptionsMenu.Update` installer retries only until `installed` or `failed`; a missing/changed hierarchy causes one terminal warning for that settings instance. It keys reinstall on changed `settingsscript.s`. Any mode selector should follow this defensive behavior and reset/reinstall when the settings singleton changes.
- The settings window can be opened outside the main menu. Selection should be disabled or display locked while `ModeLatch.InSession`; modifying the preference mid-session must not alter `Active`.
- Persist mode separately (existing `PatchOptions` file is suitable by precedent) rather than adding a field to `settingsscript.setting`, whose stock serialized shape is intentionally preserved. That persistence mechanism and default value have not been implemented for mode.

## Unknowns

- No actual selector design/label, persistence key, default behavior, or user-facing explanation for Experimental-unavailable/mismatched lobby is implemented.
- Whether lobby metadata reads are available early enough in all Steam lobby list/callback cases, and when `OnLobbyEnter` fires relative to `isConnected`, host `OnLobbyChange`, and join bootstrap, requires runtime confirmation.
- Current app/version compatibility behavior may exclude mixed Roadworthy versions, but does not identify Native vs Experimental. Mode negotiation format, compatibility/fingerprint policy, and host authority for that choice remain undefined.
- Whether experimental-only lobbies should be visible but disabled, hidden, or selectable with a rejection message is a product choice; only the code hooks are inventoried.
- Failed Steam create/join callbacks, password rejection, kick, duplicate lobby callbacks, host migration and reconnect have not been integrated with `ModeLatch`; state cleanup/race behavior is unverified.
- Native `ProcessMessage` admits `mapStuff` under the existing bridge gate before `RecMapStuff` changes menu state; no mode-aware gate exists today. `StableGameBridge.AllowIncoming` is structural/session safety logic, not a Native/Experimental router.
