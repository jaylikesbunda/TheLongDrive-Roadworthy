# Multiplayer Vehicle Slice Inventory

Static source inventory for the first vehicle replication slice. Native references are from `.local-analysis/all/Assembly-CSharp.decompiled.cs`; Roadworthy references are from `tools/PatchStability.cs` and `runtime/`. This records confirmed source behavior, not verified two-peer runtime results.

## Identity and persistence

| Path | Confirmed behavior | Roadworthy interaction |
|---|---|---|
| `savedatascript.GetNewKey()` | Starts from `savedata.lastID`, raises it above `ignoreSaveLastID`, all live `items` keys and saved `itemData.items[].id`, increments and returns. `GetNewKeyIgnoreSave()` uses its separate `ignoreSaveLastID` and live IDs. | `PatchStability.ConnectedReplacement` wraps both methods: disconnected play branches to original body; connected session calls `StableGameBridge.NewKey`. `NewKey` delegates to `StableNode.AllocateID`, checking both `save.items` and persisted item records. Host session setup raises saved `lastID` to node `LastID`. `StableCore` assigns each peer a `[FirstID, LastID]` range and refuses exhausted allocation. |
| `savedatascript.AddNew` / `AddNew(_tosave,key)` | Adds a live `tosaveitemscript` under its ID, sets `idInSave`, then calls `AddedNew`; explicit-key overload silently does nothing on collision. | ID allocator is the collision-avoidance boundary for patched allocations. Explicit-key call sites and behavior on collision remain to be audited for every spawn source. |
| `SaveToDictionary` / `SaveToData` | Serializes `save_item` identity, prefab ID, globalized position and rotation, buried flag, and component records such as car, engine, attachable, bus doors, parts, tanks, etc.; it updates an existing item record by ID or appends one. `SaveToData` is the overall data save entry point. | Patch inserts `RequireConstructionSettled` at `SaveToDictionary` and `BeforeNativeSaveData` at `SaveToData`; native bodies are retained. MP ownership flags (`mppickedup`, `mpequipped`, `mpstored`, `mpweared`) are live fields on `tosaveitemscript`; no matching fields were observed in `save_item` construction/serialization, so durable persistence of transient player ownership is not established. |
| `RearrangeID` | Builds old→new ID map and rewrites `save_attachable.parentid`, physics-lock member IDs, and many per-component record IDs when importing/rekeying saved item data. | IDs are structural references, not just labels. Any new allocator/import path must remap child/parent/component references consistently. |

## Native spawn, load and stream-in/out

- Native saved-world loading uses `savedatascript.SpawnItem(save_item)`, which resolves a prefab (or map placement) and instantiates at the record's global position/rotation; then `InitAfterSpawn(GameObject,key)` calls `tosaveitemscript.FStart(key)` and makes its rigidbody kinematic if present; `LoadStuff(savedata,key,clientDontAskOnSpawn)` restores the record's component state once.
- In `LoadStuff`, a non-host/non-single client normally sends `syncScript.s.SendAskItemData(key)` and returns unless `_clientDontAskOnSpawn` is true. The state is applied only if the corresponding item exists and `loaded` is false. `ProcessMessage` routes `askItemData` to `syncScript.RecAskItemData(sender,bytes)`; data response/replay includes item pose plus component state. The exact complete response ordering across all component types was not independently reconstructed here.
- `savedatascript` keeps live items in `items` and far/persisted records in `data.itemData.items`, with `itemChunks` keyed by global X/Z chunks of `itemChunkSize = 25,000`. `AddToFarStuff` stores the record and records its chunk. `LoadStuff` is demand-loaded; a streaming method owns creation/teardown. The full exact camera-distance thresholds and every transition call path have not been traced for this slice.
- Native `tosaveitemscript.MultiUpd()` runs only while connected: tanks check sync time; stale non-owner pose can trigger `askItemPos`; current owner sends changed local/global/player/car pose via `ForcePosUpd`, with extra updates for selected moving/picked-up objects. `syncScript.SyncStuff()` normally walks live `savedatascript.s.items` in batches; Roadworthy replaces this coroutine with `StableGameBridge.SyncItems` while retaining native per-item updates.
- Native `ForcePosUpd` distinguishes loose/global items (`itemPosGlobal`), child or stored items (`itemPosLocal` with parent ID and slot/physics-lock index), player-held/worn/inventory items (`itemPosPlayer` relative to body/hand/head and hold type), and cars (`carPosGlobal`, plus `carVelocity`). It may send item velocity or ragdoll state too. Car position is global regardless of player-held state.
- On receive, `ProcessMessage` dispatches those packet types to `RecItemPosGlobal`, `RecItemPosLocal`, `RecItemPosPlayer`, `RecCarPosGlobal`, `RecItemVelocity`, or `RecCarVelocity`. A receiver that cannot resolve the item may request item data. `RecItemPosPlayer` sets runtime MP held flags and applies the item to the remote player's hand/inventory/wear state. `ThisOneInCharge()` and related logic then use local pickup state, remote flags, host role, and car interaction role to decide who simulates/sends.
- Roadworthy adds bounded missing-item/state replay (`AttachReplay.cs`, `PendingItemQueue`) around the native receiver path. It holds item/parent-dependent native packets when either endpoint is absent, requests repair, and replays through `ProcessMessage` after IDs materialize. This buffers ordering gaps; it is not a replacement persistence registry.
- Roadworthy streaming hooks preserve native paths by default: `PatchStability` guards `roadGenScript.Upd`/`RoadAt`, `poiGenScript.GenChunk`/`AddPois`, category chunk/gen routines, and adds live/far road bookkeeping. It changes item streaming anchor selection to use a parented item's root position (`ItemStreamPolicy`) and guards `tosaveitemscript.DistUnFreezeRB`; those do not establish an entity's durable multiplayer ownership or full streaming lifecycle.

## Host world capture/apply and newly spawned items

- `StableGameBridge.CaptureWorld()` flushes deferred far placement, copies `savedatascript.s.data.itemData`, refreshes records for live items with `SaveToDictionary`, and records each live item's ID and active state. It adds saved/instantiated POI state from map generators and caches native player-position messages plus known remote player/item pose state. For locally item-owned live items it forces position capture, keeping player-held/local-parent pose messages (`itemPosPlayer`/`itemPosLocal`).
- `SendWorld(peer)` is host-only and requires initialized map/save state; it serializes/round-trips a version-3 `WorldFrame` and calls `node.BeginSnapshot`. `ApplyWorld(bytes)` validates version/fingerprint, duplicate/zero IDs, prefab resolution, active references, POI generator indices and player/item message types before replacing world state. It removes live items absent from definitions or with a mismatched prefab, assigns snapshot item data, rebuilds `itemChunks`, spawns missing active items through native `SpawnItem`+`InitAfterSpawn`, calls native `LoadStuff(..., true)`, restores active flags, loads/queues POI records, applies time delta and replays staged non-local player/item messages. `TimedApplyWorld` clears transient recovery/smoothing state first.
- Snapshot application preserves the native save representation as baseline, but is not a separately atomic transaction: a native spawn/load exception can occur after validation/world replacement begins. Rollback semantics were not found in this path and remain unverified.
- New guest-authored objects use a separate spawn handoff (`TickSpawnHandoff`/`ApplySpawn`): guest scans active live IDs inside its reserved range not yet announced; captures a bounded batch of global definitions first and then `SyncAll()` component state, filters to definition/local pose/holdable packets, caps item and packet counts/bytes, sends a sequenced transaction, and retries awaiting host ack. Host checks authenticated peer range, sequence/hash, packet framing/validity, definition-first ordering, undeleted IDs, and parent references; it applies native handlers, verifies materialized definitions and settled attachment/storage state, then publishes packets and acknowledges. This is a native handler replay pipeline, not proof of persistence to the host save on every possible component path.
- Roadworthy spawn capture is not the same as native host ownership transfer. Host-generated world capture and guest-owned object introduction are distinct flows. The source reviewed here does not show a general atomic, acknowledged ownership handoff protocol for an already-existing vehicle and all of its attached/stored contents.

## Seats, attachment and vehicle authority

- Native `seatscript.SetID` records either a saved-item parent ID or POI generator + POI position, plus seat index and parent transform. Native `fpscontroller.GetIn/GetOut` and `seatscript.GetIn/GetOut` perform local player-seat transitions and car driving flags. `FreeCanSit()` checks local occupancy and, while connected, the transient `inUseMulti` flag; the latter expires after one second.
- Native `syncScript.SendPlayerPos` includes sitting flag, `setidpoi`, player global or seat-relative pose, duck value, and either saved parent item ID + seat ID or POI generator/ID + seat ID. `RecPlayerPos` resolves the referenced live item seat or generated POI seat, parents/smooths the remote avatar and sets that seat's multiplayer-use marker/time. This is seat occupancy replication via player pose, not a durable reservation or vehicle ownership grant.
- Roadworthy wraps native `ItemPosLocal` and `UpdAttachable` iterators so the original retry loops remain active while each `MoveNext` checks its ticket. `AttachReplay` queues attachment packets when item/parent endpoints are unavailable, handles a different old slot through native detach/uncraft path, and replays via native `ProcessMessage`. `PatchStability` inserts seat entry/exit callbacks around native `fpscontroller.GetIn/GetOut` and teleport callbacks without replacing the native body.
- Native `ThisOneInCharge()` is based on remote item flags plus native `IsHost()` or locally held item/car authority. `ThisOneInChargeCar(role)` compares local `CarWhatDoing()` role against a supplied remote role when local role meets a threshold. `CarWhatDoing()` derives driving, shotgun, push-grip, picked-up, host or no-action from player state; the enum includes `driving`, `pushgripping`, `shotgun`, `pickedup`, `justHost`, `nothing`, and `notCar`.
- Roadworthy's `CarChargeGate` is a narrow guard on `ThisOneInChargeCar(remoteRole)`: for a connected guest only, if local role is `shotgun` and a known host avatar is within 400 m, it vetoes the local charge; unknown host distance falls back to native. It does not implement a complete car transfer transaction or authority epoch.
- Bus-specific Roadworthy additions use `BusSeatClaims` built from native `playerSyncClass.GotUpd` seat information; only a fresh, exact `driverSeat0` claim can back its bus-pair driver authority. Bus-pair / vehicle-motion extension messages and replicas are separate from the native car item pose stream. `MovingVehiclePassenger` adjusts local movement frame for a passenger supported by a remotely owned vehicle; its own comment says it does not move the player or transfer vehicle ownership.
- Native storage uses `mountStuff.Scan/FreezeUpd/Store/Unstore` and local physics-lock parenting. Roadworthy redirects only the `Store` call in `mountStuff.FreezeUpd` through `AutoStoreGate`; it retains the native `Store` body and other Store callers. Guest auto-store may be vetoed based on `NativeStoreGate`; native unstore observer records cargo release. This is narrower than general container ownership or transactional cargo transfer.

## Confirmed hook paths for the first slice

`PatchStability.cs` explicitly wires:

- ID allocation: `savedatascript.GetNewKey`, `GetNewKeyIgnoreSave` → connected-only node allocator.
- Native item replication: `syncScript.SyncStuff` → Roadworthy `SyncItems`; native `ProcessMessage` admission guard; native send/target send and receive poll → `RouteBroadcast`, `RouteTarget`, `ReadBudgeted`.
- Save boundary: entry hooks at `savedatascript.SaveToData`, `newSaveScreenScript.Save`, export, `SaveToDictionary`, and `SetDataFromSave`; the inventory does not claim each hook is multiplayer-specific.
- Seat/attach: native-body-preserving `fpscontroller.GetIn/GetOut` callbacks; iterator wrappers for `syncScript.ItemPosLocal` and `UpdAttachable`.
- Streaming/placement: road/POI/category gates, far-placement queue, root item stream anchor, unfreeze guard, store scan/freeze gates, and missing-item delete protection (`MayRemoveMissingItem`).
- Vehicle role: `tosaveitemscript.ThisOneInChargeCar` guard → `CarChargeGate`; remote player seat claims are observed from `playerSyncClass.GotUpd`; bridge ticks bus pair and remote passenger helpers.

## Unknowns to resolve before a full vehicle-authority design

- Exact native and patched call-site coverage for `AddNew`, explicit-key spawn, every POI/random spawn, and every spawned entity's persisted component defaults; whether all generated vehicle/part trees are captured by the guest range scanner.
- Full item load/unload distance thresholds, inactive-vs-far semantics, destruction/removal/tombstone behavior, item-chunk reindexing after motion, and saved records while a host/guest is far from the object.
- Which host/guest save records are authoritative after disconnect, late join, host departure, world replacement, or save-as; transient MP held/stored flags are not evidenced as durable save fields.
- Complete native `RecCarPosGlobal`/`RecCarVelocity` effects and all vehicle-specific component sends/receives under simultaneous driver/passenger/push/pickup actions; role values and the narrow shotgun fix do not alone establish conflict-free authority.
- Atomic ownership transfer of vehicle + occupants + attached parts + stored cargo, including epoch/lease, ack/rollback, disconnect recovery and old-owner packet rejection. Existing bus-pair protocol does not prove this for every car.
- Seat claims for non-bus cars/POI seats, stale claims during packet loss, same-seat contention, and consistency between native `inUseMulti` timeout and Roadworthy's bus claim freshness.
- Snapshot failure rollback and interaction between native asynchronous placement/load, pending attach replay, POI reconstruction and the host's dynamic object records.


## Vehicle-group ID remap checklist and `RearrangeID` risks

**Native evidence (decompile line numbers):** `savedatascript.RearrangeID(itemDataClass,uint)` is at `Assembly-CSharp.decompiled.cs:48019–48075`. It builds `old save_item.id → offset + ordinal` from `_itemData.items` (`48021–48027`), then rewrites attachment parent IDs (`save_attachable.parentid`, `48028–48034`), every stored-child ID in `save_physicslock.IDs` (`48035–48048`), and the per-record owner `id` for the `iid`/`iid2` component collections (`48049–48074`). The data container's exact lists are `itemDataClass.items`, `partconditions`, `ammo`, `weapon`, `tanks`, `usable`, `meter`, `car`, `engine`, `attachable`, `nyul`, `ragdollpos`, `busdoorscript`, `colors`, `slideOnCollider`, `rendszam`, `randoms`, `door_rots`, `ginlamp`, `wear`, `food`, `outfit`, `randomScales`, `newai`, `painting`, and `physLocks` (`48628–48680`). Generic `RearrangeID1/2` changes only the record's own `id` when found in the map (`48555–48579`).

Vehicle-related persisted relations confirmed by source:

- An attachment record is keyed by the child ID (`save_attachable.id`) and, for `attachType == toItem`, stores `parentid` plus collider/slot `indexType` and `index`; local/global attachment poses are also persisted (`save_attachable.Save`, `63407–63513`). `save_attachable.Load` resolves a parent through `itemPlaceRemoveScript.GetOne(parentid)` and then resolves collider/slot by index (`63516–63560`). A mounted part group's IDs and slot references therefore need to stay coherent.
- A physics-lock/storage record is keyed by the parent ID and slot index (`save_physicslock.id`/`ind`), with `IDs[]` containing each stored child's save ID and matching local `poss[]`/`rots[]` (`65119–65129`, `65154–65195`). Loading resolves each child by ID, restores local transform, then calls `mountStuff.Store` (`65203–65220`). `RearrangeID` rewrites both the physics-lock record's owner ID through `RearrangeID2` and its child references explicitly.
- The main `save_item` record carries the object's `id`, prefab ID and transform, while `save_carscript` and other component records are keyed by that item's ID. Native `LoadStuff` loads all of these component lists against the spawned object's `idInSave` (`savedatascript.LoadStuff`, `48122–48223`).

**Checklist before using this routine for a multiplayer vehicle group:**

1. Define the exact closed group: vehicle root, every mounted/attached child, every stored child and nested stored group, plus all component records. Build an explicit old→new map for every `save_item.id`; reject missing definitions and duplicate old IDs before mutation.
2. Remap every owner key in every `itemDataClass` component list named above. For references, rewrite `save_attachable.parentid` and each `save_physicslock.IDs[]` element. Preserve POI/world parents only as explicit external references; otherwise reject a group that references a parent outside the transferred set. Validate each remapped attachment/storage parent and each slot/lock index against the recipient prefab before spawning.
3. Reserve a contiguous target ID block for the entire group, not just one ID. Construction spawn calls `RearrangeID(construction.itemData, 1)` when saving selected objects (`kaposztaleves.SaveSelected`, called from `PressedSaveCar`/`PressedSaveMarked`, at `33448–33512`) and calls `RearrangeID(construction.itemData, savedatascript.s.GetNewKey())` before importing/spawning the construction (`PressedSpawnConstruction` at `33514–33548`). `GetNewKey()` returns one ID; `RearrangeID` assigns that ID and following ordinals to the full item list. A multiplayer allocator must reserve/check the whole count against both local/save IDs and the session's `[FirstID,LastID]` range before this mutating call.
4. Check arithmetic and collision bounds before changing any field: `RearrangeID` uses `uint num` and unchecked `num++` (`48021–48027`), does not test overflow/zero, target collisions, source uniqueness, or transaction atomicity. `dictionary.Add` throws for duplicate old IDs. Preflight must prevent partial/failed remaps and avoid ID 0 or wraparound.
5. Make the operation safe for malformed/legacy data. `RearrangeID` checks a `save_physicslock` for null but dereferences `physLock.IDs.Length` without a null check (`48035–48048`); the native `save_physicslock.Load` explicitly treats `IDs == null` as an empty/no-op record (`65203–65208`). Null stored-ID arrays can therefore make import remapping throw. The method also iterates all component collections without null checks; ensure deserialized `itemDataClass` lists are initialized or reject/normalize before invoking it.
6. Treat `RearrangeID` as an in-place constructor/import helper for detached `itemDataClass`, not a live-world transfer. It does not update `savedatascript.items` dictionary keys, `itemChunks`, live component IDs, pending pose/attach/storage messages, Roadworthy spawn ledgers/announced ID sets, player inventories/seats, or existing ownership claims. A live remap would require coordinated index/packet/owner updates or should be forbidden.
7. After remap, round-trip or independently validate every owner/reference before applying. Native `save_attachable.Load` and `save_physicslock.Load` can materialize dependencies via `GetOne`/`PlaceOne`; failures may leave a partially built vehicle graph. Keep definitions ahead of reference/state application and do not commit ownership until all required parts/storage settle.

**Roadworthy boundary:** `SpawnCoordinator` is a frame-budgeted world-mutation scheduler, not an ID allocator/remapper. Its `SpawnJobKey` is world generation + source + key + owner (`runtime/SpawnCoordinator.cs:29–66`); it admission-checks duplicate/stale/capacity/dependencies and serializes mutation work (`152–205`, `595–613`). `StableGameBridge` uses it for deferred far placement and POI construction, then fences save/world capture on pending work (`StableGameBridge.cs:1197–1212`, `2021–2078`, `2154–2166`). Guest `TickSpawnHandoff` instead selects active objects already inside the peer's reserved ID range, captures definitions and state, and host `ParseSpawnLedger` requires each packet ID in that range and attachment/storage parent resolution (`StableGameBridge.cs:3260–3300`, `3313–3378`); it does not call `RearrangeID`. Thus the existing coordinator/handoff can schedule and validate construction/spawn, but neither provides a vehicle-group rekey/ownership transfer transaction.

## Native `itemDataClass.Copy` fidelity

The decompiled `itemDataClass.Copy(itemDataClass)` (`Assembly-CSharp.decompiled.cs:48682–48709`) visits all 26 save lists in `itemDataClass` (`48628–48680`) through `savedatascript.Copy<T>` (`48518–48535`). Comparison of each supported record's top-level data fields against its `Copy` body found no omitted fields. Mutable nested data is copied rather than shared: for example `save_item.transform` is a value struct (`62200–62206`, `62252–62268`); `save_partcondition.color` and `save_weapon.bbgun/revolver` use copy constructors (`62366–62378`, `62552–62562`); and tanks, meter records, ragdoll transforms, bus-door arrays, outfit segments, random-scale vectors and physics-lock `IDs/poss/rots` arrays are recreated (`62823–62864`, `63045–63060`, `63160–63191`, `63823–63839`, `63923–63958`, `64751–64772`, `64816–64829`, `64908–64928`, `65228–65273`).

This is fidelity for ordinary valid records, not a robust detached-clone boundary. `savedatascript.Copy<T>` clears the destination list before copying and calls `_from[i].Copy()` without a null-entry check (`48518–48535`); a null element throws after prior lists/elements may already have been overwritten. If source and destination are the same list, clearing the destination also erases the source before iteration. If the destination list is null, assigning a replacement only updates the local parameter, not the owning `itemDataClass` field. Validate list initialization/null entries and ensure source/destination do not alias before using native `itemDataClass.Copy` for admission or remapping. Some array-copy routines normalize null and empty arrays to null; notably `save_revolver.Copy` does so for `bullets`, while `save_revolver.Load` indexes `bullets.Length` without a null check (`62714–62736`, `62698–62708`). Empty revolver arrays therefore require explicit rejection or normalization before native load.

**Nested record and remap mismatch:** Several records embed other `iid`/`iid2` objects, but native `RearrangeID` only remaps each top-level list entry's ID (generic `RearrangeID1/2`, `48555–48579`) and does not recurse into those fields. This leaves embedded IDs stale after import rekeying:

- `save_weapon.Save` stores optional `save_bbgun` and `save_revolver` children using the owning item's `_id` (`62511–62520`); both nested classes implement `iid` (`save_bbgun: 62570–62578`, `save_revolver: 62643–62654`). `RearrangeID` remaps the `weapon` list entry only (`48052`), so the nested `bbgun.id` / `revolver.id` remain the old item ID. In addition, `save_weapon.Copy` always constructs both children (`62552–62559`); their copy constructors leave a default object when the source child is null (`save_bbgun.Copy: 62628–62637`, `save_revolver.Copy: 62714–62736`). A missing source revolver can therefore become a non-null child with `bullets == null`, and `save_revolver.Load` dereferences `bullets.Length` (`62698–62708`). A missing bbgun can become a zero-valued child and overwrite prefab state if the target item has that component (`save_weapon.Load: 62530–62543`). Preserve null children or reject them before native copy/load; explicitly remap/validate nested IDs if the rekeyed representation requires identity consistency.
- `save_partcondition.Save` embeds `save_color` with the same item ID and component index (`62332–62340`); `save_color` implements `iid2` (`63962–63976`). `save_partcondition.Copy` constructs a child even when `_from.color` is null (`62366–62380`). `RearrangeID` remaps the outer `partconditions` entry (`48050`) and the separate top-level `colors` list (`48062`), but not this embedded color ID/index. `save_partcondition.Load` applies the embedded color (`62347–62360`), so any import remap must account for the nested copy, not assume the outer remap covers it.
- `save_meterscript` embeds `save_meter[]` records (`63032–63042`), each with an `iid` (`62969–62978`). `mutatok` records are saved with the owner `_id` (`63101–63108`); `RearrangeID` remaps only the top-level `meter` owner (`48055`), not the embedded IDs. `Copy` deep-copies these arrays but turns null array elements into default non-null `save_meter` objects because the child `Copy` is a no-op on null (`63045–63056`, `63160–63191`). Meter load matches by `tipus` rather than nested ID (`63126–63157`), so the stale IDs may not break that load path, but they remain inconsistent serialized identities.
- `save_outfit.Copy` likewise turns null `segments[]` entries into default segments (`64751–64772`, `64816–64829`); these records have no `iid`, so this is a null/data-fidelity difference rather than a `RearrangeID` omission.

Before using native copy/remap as the basis of a vehicle admission transaction, preserve optional nested-record nulls, define whether embedded IDs are aliases or independent identities, and make the mapping cover every embedded owner ID that is meant to change. The current Roadworthy spawn range validation does not exercise these nested-record cases.

Additional detached-record test: `save_weapon.Copy` constructs a `save_revolver` even when the source's revolver is null, producing a new revolver record with null bullets. The actual game types reproduce this without opening a save. The experimental detached remapper currently rejects all weapon records until a tested normalization policy can preserve absent nested components and valid ammunition arrays. The scalar-only audit does not detect nested null-to-object changes.

Another detached-record assertion shows native `RearrangeID` changes the outer weapon record's ID but leaves an embedded `save_revolver.id` unchanged. Whether that nested ID has any effect in a particular load path remains unverified; do not infer that it is safe merely because the outer ID changed.
